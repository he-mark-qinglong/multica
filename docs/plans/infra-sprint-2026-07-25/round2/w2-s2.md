## W2-T3 — ingest 层 profit_factor 兜底推导（metric.go）

- **目标**：blob 缺 `profit_factor` 时，从同 blob 的 `daily_returns`/`daily_pnl`/`equity_curve`/`nav_curve` 数组推导 PF；并同步两处过时注释。
- **读**：`server/internal/handler/metric.go`；蓝本 `quant-loop/research/swarm/2026-07-25/gate-ledger-fix/metric_proposal.go`（117 行，全文照抄其三个函数）。

- **机器**：either（只需 Go 工具链）· **估时**：15 min · **依赖**：无（纯函数独立；不 import gate 新常量）。

### 步骤

1. **加 import**：`metric.go:3-14` import 块加 `"math"`。
2. **加三个纯函数**：把 `metric_proposal.go:20-100` 的 `computeProfitFactorFromDailyReturns`、`equityCurveToReturns`、`extractDailyReturns` 原样复制到 `metric.go`（建议放在 `jsonNumber`(:72) 之后、`parseRunMetricJSON`(:79) 之前）。去掉 PROPOSAL 头注释，函数 doc 注释保留。
   - 注意：`extractDailyReturns` 里 `case []float64:` 分支在 `json.Unmarshal` 进 `map[string]any` 后是死代码（JSON 数组只解成 `[]any`），**照抄保留**作防御，不要"简化"掉。
   - 混合类型数组（如 `[0.01, "x"]`）必须返回 `nil, false`，这是提案的明确语义，勿改。
3. **插兜底块**：在 `parseRunMetricJSON` 的 floatCols 循环结束之后（`:104` 的 `}` 之后）、`if v, present := obj["oos_windows"]`（`:106`）之前，插入：

```go

	// derive it from a daily-return / equity-curve array in the same blob.
	if f.ProfitFactor == nil {
		if rets, ok := extractDailyReturns(obj); ok {
			if pf, ok := computeProfitFactorFromDailyReturns(rets); ok {

			}
		}
	}
```

4. **同步两处注释**（不改逻辑）：

### 步骤（7 个用例，全部放 `package handler`，无需 DB 连接即可逻辑通过）

1. `TestComputeProfitFactorFromDailyReturns`：
   - `[0.02, -0.01, 0.03, -0.01]` → pf = 0.05/0.02 = 2.5, ok=true。
   - `[0.01]` 和 `[]` → ok=false。
   - `[0.01, 0.02]`（全盈无亏）→ pf = `math.Inf(1)`, ok=true（用 `math.IsInf(pf, 1)` 断言）。
   - `[0, 0]` / `[-0.01, -0.02]`（无盈利）→ ok=false。
2. `TestEquityCurveToReturns`：
   - `[100, 110, 99]` → `[0.10, -0.10]`（用 1e-9 容差比较）, ok=true。
   - `[100]` → ok=false；`[100, 0, 5]`（前值为 0）→ ok=false。
3. `TestExtractDailyReturns`：
   - `{"daily_returns": [0.01, -0.02]}` → 原样返回 `[0.01, -0.02]`。
   - `{"equity_curve": [100, 110, 121]}` → 返回 `[0.10, 0.10]`（容差断言），即先转收益率。
   - `{"daily_returns": [0.01, "bad"]}` → ok=false（混合类型拒收）。
   - `{"daily_returns": "not-an-array"}` 和 `{}` → ok=false。
   - 优先级：`{"daily_returns": [...], "equity_curve": [...]}` → 命中 `daily_returns`（key 顺序 daily_returns > daily_pnl > equity_curve > nav_curve）。
4. `TestParseRunMetricJSONProfitFactorFallback`（核心）：
   blob `{"sharpe": 2.0, "daily_returns": [0.02, -0.01, 0.03, -0.01]}` → `f.ProfitFactor != nil && *f.ProfitFactor == 2.5`（容差）。
5. `TestParseRunMetricJSONProfitFactorFromEquityCurve`：
   blob `{"sharpe": 2.0, "equity_curve": [100, 110, 99, 108.9]}` → returns `[0.1, -0.1, 0.1]` → PF = 0.2/0.1 = 2.0（容差断言）。
6. `TestParseRunMetricJSONExplicitPFWins`：
   blob `{"profit_factor": 1.8, "daily_returns": [0.02, -0.01]}` → PF 仍为 **1.8**（显式值优先，兜底只在 nil 时触发）。同时确认现有 `TestParseRunMetricJSONCanonical`（已断言 pf=1.8）不受影响。
7. `TestSharpeOnlyBlobGateFails`（**依赖 T1**，T1 未合入则此用例会红）：
   ```go
   f, ok := parseRunMetricJSON([]byte(`{"sharpe": 31.7}`))
   if !ok { t.Fatal(...) }
   status, _ := gate.Evaluate(gateMetricsFromFields(f))
   if status != "fail" { t.Errorf("sharpe-only blob gate = %q, want fail", status) }
   ```
   文件顶部 import 需加 `"github.com/multica-ai/multica/server/internal/gate"` 和 `"math"`（按用例实际用到再加）。
   语义依据：strict gate 下 6 条规则全 required，sharpe 在场但其余 5 项缺失 → failed=true 且 sharpeMissing=false → `"fail"`（而非旧的 pass，也非 no-data——no-data 只在 sharpe 本身缺失时）。

## W2-T5a — DB 迁移 125：gate_status CHECK 约束

- **目标**：新增迁移 125，给 `run_metric.gate_status` 加 CHECK，只允许 `pass`/`fail`/`no-data`/NULL。
- **读**：`server/migrations/123_run_metric_gate.up.sql`（确认列存在、无既有约束）；`server/migrations/124_issue_claim_columns.up.sql`（编号/风格参考）。
- **写**（新建 2 个文件，改 0 个既有文件）：
  - `server/migrations/125_run_metric_gate_status_check.up.sql`
  - `server/migrations/125_run_metric_gate_status_check.down.sql`
- **机器**：**mac**（本地 postgres 可实测迁移；无库时降级为静态验收）· **估时**：10 min · **依赖**：无。

### 步骤

1. `125_run_metric_gate_status_check.up.sql` 全文：

```sql
-- gate_status gains a third value "no-data" (sharpe absent → nothing to
-- judge) alongside "pass"/"fail". Migration 123 added the column without a
-- CHECK constraint, so the DROP below is a defensive no-op on fresh
-- databases; the ADD is the real change. The partial index from 123
-- (idx_run_metric_workspace_gate) already covers all three values.
ALTER TABLE run_metric
    DROP CONSTRAINT IF EXISTS run_metric_gate_status_check;

ALTER TABLE run_metric
    ADD CONSTRAINT run_metric_gate_status_check
    CHECK (gate_status IS NULL OR gate_status IN ('pass', 'fail', 'no-data'));
```

2. `125_run_metric_gate_status_check.down.sql` 全文：

```sql
ALTER TABLE run_metric
    DROP CONSTRAINT IF EXISTS run_metric_gate_status_check;
```

3. 不要加数据 backfill（存量行由部署后 `POST /api/metrics/reevaluate` 重算，属另一片的部署任务 T11）。
4. 编号确认：`ls server/migrations/ | sort | tail` 顶部应为 `124_*`，若 125 已被别人占用则改用下一个空闲号并同步两个文件名。

## W2-T5b — reevaluate 响应加 no-data 计数（metric.go）

- **目标**：`POST /api/metrics/reevaluate` 响应 JSON 增加 `"no-data"` 计数；`reevaluated` 口径含 no-data（这些行实际被重算并写库了）。
- **读**：`server/internal/handler/metric.go:482-552`（`ReevaluateRunMetrics` 全函数）。
- **写**：`server/internal/handler/metric.go`（只动 `ReevaluateRunMetrics` 函数体内 2 处，~523 与 ~545-551 行）。
- **机器**：either · **估时**：10 min · **依赖**：T3（同文件串行，T3 先合）。

### 步骤

1. **counts 初始化**（`:523`）：
   ```go
   counts := map[string]int{"pass": 0, "fail": 0, "skipped": 0, "errors": 0}
   ```
   改为：
   ```go
   counts := map[string]int{"pass": 0, "fail": 0, "no-data": 0, "skipped": 0, "errors": 0}
   ```
   中间循环（`:524-543`）**不动**：`status == ""` → skipped 分支保留（strict gate 下变为防御性死分支，仍正确）；`counts[status]++` 对 `"no-data"` 自动落入新 key。
2. **响应体**（`:545-551`）改为：
   ```go
   writeJSON(w, http.StatusOK, map[string]any{
       "reevaluated": counts["pass"] + counts["fail"] + counts["no-data"],
       "pass":        counts["pass"],
       "fail":        counts["fail"],
       "no-data":     counts["no-data"],
       "skipped":     counts["skipped"],
       "errors":      counts["errors"],
   })
   ```
   理由：`status != ""` 的行都被 `SetRunMetricGate` 实际写库，no-data 行计入 reevaluated 才与"重算并落库"语义一致。`skipped` key 保留（兼容既有消费方，恒为 0）。
3. 不改函数签名、路由注册、请求解析；不碰文件内其他函数。
